# recon — разведка чужого репо

Референс к режиму `recon` (SPEC.md §7). Нарратив по образцу `repo-analyzer`
(адаптивный опрос, субагенты по модулям, содержательные связки), плюс
поведенческий слой, которого у `repo-analyzer` нет: git-история чужого репо.

## 1. Когда recon, а не audit

Граница — не тип репозитория, а вопрос пользователя.

| Признак | `recon` | `audit` |
|---|---|---|
| Вопрос пользователя | «как это устроено», «расскажи», «на что это похоже», «стоит ли туда лезть» | «что не так», «почему больно», «что чинить» |
| Триада intent/structure/behavior | инструмент карты — показывает, где расходится намерение, форма и практика | гейт допуска находки (§2 SPEC) — 2 оси = `finding`, 3 = `verdict` |
| Risk-каталог R1-R6 (§5 SPEC) | не применяется как каталог для флагов; словарь можно использовать описательно | применяется, каждая находка получает risk-код |
| `severity`, `remedy`, `gain`, `alternatives` | не назначаются никогда | обязательные поля формы находки (§4 SPEC) |
| Калибровка (`measure.py`, `calibrate()`), admission gate | не запускается | обязателен перед любой находкой (§6 SPEC) |
| Выход | нарративный отчёт (`ANALYSIS_REPORT.md`-аналог) | леджер (`findings.csv`) + отчёт с verdict |
| Что можно сказать о наблюдении | «модуль X правился 40 раз за полгода» — факт | «модуль X — R2, cost Pain2×Spread3, remedy: …» — находка |

**Тест на границе.** Если ответ пользователя изменил бы, чинить ли что-то в
репозитории — это `audit`, и запускать его можно только по прямой просьбе
владельца кода. `recon` не предлагает лечения чужого репозитория ни в каком
виде, даже вежливом («стоило бы...», «имело бы смысл...») — это уже суждение,
которое запрещено до `judge`-фазы (§3 SPEC) и в recon не разрешено вовсе.

Внешний ресёрч (сравнение с конкурентами, репутация проекта, паблик-дискуссии)
— не переизобретается внутри recon, это зона `deepdive` (§10 SPEC). Recon
читает только то, что лежит в самом репозитории и его git-истории.

## 2. Фазы режима

| Фаза | Что делается | Гейт перехода дальше |
|---|---|---|
| 0. Контракт разведки | Снэпшот идентичности (remote, branch, HEAD, чистое/грязное дерево); масштаб — `cloc`/`wc -l` по каталогам, не на глаз; выбор уровня глубины (см. §3) | Снэпшот и масштаб записаны в файл плана, не только сказаны в чате |
| 1. Внутренний контекст | README, CONTRIBUTING, `docs/`, ADR, комментарии-манифесты | По каждому источнику — выжимка или явное «не найдено»; молчаливый пропуск запрещён |
| 2. Признаки + опрос | Быстрый скан входных точек, зависимостей, `git log --oneline -20` по объёмным каталогам; вопросы пользователю (см. §4) | Пользователь ответил на вопросы раунда или явно передал решение агенту |
| 3. Нарративная архитектура | Деление на core/second модули, порядок глав, черновик мостов между главами (см. §8) | План глав с мостами существует как файл на диске до запуска субагентов |
| 4. Параллельный разбор | Субагент на каждый core-модуль + один батч-субагент на все second (см. §5, §6) | Все субагенты завершены, ни один не «завис» (см. §7) |
| 5. Кросс-валидация | Точечная перепроверка 2-3 выводов на модуль по исходникам; сверка поведенческого слоя с реальным `git log`; проверка непротиворечивости мостов | Расхождения найдены и исправлены в черновиках, а не перенесены в финал |
| 6. Гейт покрытия | См. §9 | Покрытие по каждому модулю ≥ порога уровня или явно объяснено, почему нет |
| 7. Сборка | Финальный нарратив: мосты вписаны, поведенческий слой вплетён по ходу текста, а не вынесен отдельной главой «история коммитов» | Готовый файл не содержит ссылок на черновики («см. черновик 6») |

## 3. Три уровня глубины

Покрытие считается как в `repo-analyzer`: **доля реально прочитанных строк**
(объединение диапазонов, запрошенных через Read) от общего числа строк файла
— не оценка на глаз.

| Уровень | Покрытие core | Покрытие second | Когда |
|---|---|---|---|
| Быстрый | ≥30% | ≥10% | нужен общий обзор за один присест, впервые видишь репо |
| Стандартный (по умолчанию) | ≥60% | ≥30% | обычная разведка перед тем как работать в чужом коде |
| Глубокий | ≥90% | ≥60% | due diligence перед интеграцией/вендорингом/миграцией на этот код |

Правила счёта, обязательные на всех трёх уровнях:

- **Сегментированное чтение файлов >500 строк.** Один сплошной Read не считается
  добросовестным покрытием. Обязательные сегменты: (а) первые ~100 строк —
  импорты и объявления типов, (б) core-логика — функции, на которые указывает
  структура каталога/имена, и на которые указывает поведенческий слой
  (хотспоты из `behavior.py`, см. §10), (в) хвост файла — тесты/экспорт, если есть.
- **«Прочитано <30% — не считово».** Если совокупно прочитано меньше 30% файла,
  покрытие этого файла фиксируется как 0%, а не как частичный процент. Нельзя
  накопить «покрытие» из пяти файлов, беглым взглядом пройденных по 10%.
- **Автогенерированный код** (protobuf, lock-файлы, миграции с автодампом схемы)
  снижает требование к построчному чтению — достаточно просканировать структуру
  и зафиксировать это явно, не подставляя фиктивный процент.
- **Не верить именам** (принцип §3 SPEC) распространяется и на recon: файл
  называется `validate_input.py` — открой и проверь, что он валидирует; каталог
  называется `domain` — проверь, что там домен, а не прокладка до контроллеров.

## 4. Адаптивный опрос

Вопросы рождаются из наблюдений, а не из чек-листа. Эвристика:

| Наблюдение | Тип вопроса | Пример |
|---|---|---|
| Самопальная реализация вместо стандартной библиотеки/сервиса | Мотив | «Свой X вместо готового Y — ограничение среды или осознанный выбор? Смотрю дальше по git-истории, если не знаешь» |
| Модуль визуально с большим fan-in/fan-out (структурная ось ещё не посчитана скриптом) | Приоритет | «Этот модуль — предмет разведки, или он вне интереса и можно пробежать по верхам?» |
| `git log` показывает частые ревёрты/переписывания одного файла | Траектория | «У этого файла бурная история (N ревёртов) — знаешь контекст, или разведке стоит его раскопать?» |
| README/ADR обещают одно, структура каталогов показывает другое | Напряжение intent/structure | «Документация обещает слои, каталоги их не показывают — это устарело или тебе интересно, где именно разошлось?» |
| Домен размазан по нескольким несмежным каталогам | Аудитория разведки | «Цель — понять, чтобы встроиться рядом, или понять, можно ли туда вообще безопасно писать?» |
| Мало истории / молодой модуль | Ограничение оси | «Поведенческая ось здесь недоступна (мало коммитов) — это ожидаемо (новый код) или само по себе интересно?» |

**Критерии хорошего вопроса**: основан на конкретном наблюдении (не абстрактная
анкета), влияет на дальнейший ход разведки (ответ реально меняет, что читать
дальше и с каким акцентом писать), пользователь может ответить сходу, не
дублирует то, что и так можно узнать из кода/git без его участия.

**Лимит**: не больше 3 вопросов за один раунд (`AskUserQuestion`). Раундов —
сколько нужно: новое наблюдение в ходе фазы 4/5 может породить ещё один
короткий раунд.

## 5. Промпт-шаблон: субагент по core-модулю

```
Ты — архитектор-разведчик. Разбираешь модуль «{модуль}» в чужом репозитории
{репо}. Это RECON, не AUDIT: тебе запрещено ставить severity, предлагать
лечение, оценивать риск по каталогу R1-R6. Твоя работа — описать, что есть
и как оно ведёт себя на практике, а не что с этим не так.

## Контекст проекта
- Назначение: {одна фраза}
- Общая архитектура: {стиль, ключевые решения}
- Место модуля в системе: {как связан с соседями}

## Нарративный контекст (обязательно использовать)
- Что рассказала предыдущая глава: {краткое резюме}
- С каким вопросом читатель входит в эту главу: {вопрос}
- Что нужно подготовить для следующей главы: {задел}

## Файлы в зоне ответственности
{список путей}

## Структура анализа (10 пунктов)
1. Роль в системе — deletion test (§8 SPEC): что случится с системой,
   если модуль удалить мысленно; кто у него единственный/множественный вызывающий
2. Проблема, которую модуль решает — без него что делали бы иначе
3. Замысел — выбранный подход; альтернативы, которые видно, что отбросили
   (по комментариям, по истории, по несостоявшимся веткам кода)
4. Ключевые контракты/структуры данных — только то, что нужно для понимания
   решения, не полный листинг типов
5. Основной поток исполнения — Mermaid-диаграмма + путь file:line
6. Связь с другими модулями — кто зависит, от кого зависит; виден ли шов
   (§8 SPEC: место, где поведение можно подменить не правя исходник) или
   граница держится только на соглашении
7. Поведенческий слой — что говорит git-история именно об этом модуле:
   сколько раз переписан, какие баги здесь чинили, что откатывали
   (конкретные команды и как их использовать — референс §10 этого файла)
8. Наблюдения без вердикта — то, что бросается в глаза, сформулировано как
   факт («X сделано так»), не как находка («X сделано плохо»); никакого risk/remedy
9. Открытые вопросы — что не удалось выяснить по коду и истории, что стоит
   спросить у автора
10. Нарративный мост — 1-2 фразы в начале главы (связь с предыдущей), 1 фраза
    в конце (задел на следующую); мост объясняет, почему следующий модуль
    вообще существует, а не просто анонсирует его (см. §8 этого файла)

## Дисциплина
- Не верить именам файлов/каталогов/функций — открывать и проверять
- Не выходить за пределы списка файлов из раздела выше
- Кросс-модульные выводы помечать «[ПРОВЕРИТЬ ГЛАВНЫМ]» — сверит на фазе 5

## Запись
Пиши в {work_dir}/drafts/module-{модуль}.md. Для модуля >5000 строк —
инкрементально: первая подсистема через Write, следующие через Edit,
не жди, пока прочитаешь всё.

## Требование покрытия
Уровень разведки: {уровень}. Минимальное покрытие core: {порог}%.
В конце черновика — таблица покрытия: файл | строк всего | строк прочитано |
% | причина непокрытого. Итоговая строка — ✅/❌. Не дотянул — дочитывай.
```

## 6. Промпт-шаблон: батч-субагент по second-модулям

```
Ты — архитектор-разведчик. Быстро проходишь второстепенные модули
{репо}: {список модулей с предполагаемой зоной ответственности и файлами}.
RECON, не AUDIT — без severity и remedy.

## Контекст проекта
- Назначение: {одна фраза}
- Общая архитектура: {стиль}

## На каждый модуль — по одному абзацу
1. Ответственность (одна строка)
2. Роль в целом (одна строка): зачем он вообще существует
3. Как реализовано (одна строка)
4. Поведенческий след (одна строка): «менялся часто/редко, последний раз — {когда}»,
   по данным `git log --oneline -- {путь}` или сводки `behavior.py`
5. Если есть что-то нетривиальное — отдельный абзац, иначе не разворачивать
6. Список файлов

## Запись
{work_dir}/drafts/module-secondary.md

## Требование покрытия
Уровень разведки: {уровень}. Минимальное покрытие second: {порог}%.
Таблица покрытия в конце — тот же формат, что у core-модулей.
```

## 7. Дисциплина ожидания субагентов

- После запуска субагентов главный агент **не читает** файлы, порученные
  им, — граница по списку файлов в промпте держится и с его стороны.
- Пока субагенты работают, главный агент занят: внутренним контекстом уже
  прочитанным на фазе 1, черновиком мостов, подготовкой сквозного
  поведенческого среза по всему репо (топ хотспотов `behavior.py` — материал
  для фазы 5, не для перехвата чужих файлов).
- **Критерий «завис»**: в файле-черновике субагента больше 5 минут нет новых
  строк. Только после этого главный агент вправе перехватить именно этот
  модуль — не раньше и не «на всякий случай».
- **Запрет на опережение**: сведение (фаза 7 — сборка) не начинается, пока не
  завершены **все** субагенты, включая батч по second-модулям. Готовность
  части core-модулей не повод начинать писать финальный текст.

## 8. Нарративные связки

Плохая связка не создаёт содержательного моста, только объявляет порядок:

> ❌ «Далее рассмотрим модуль X.»

Хорошая связка объясняет, почему следующий модуль вообще существует —
через ограничение или вопрос, оставленный предыдущим:

> ✅ «Gateway решил, кто может войти, но не решает, что можно делать, попав
> внутрь — этим уже занимается policy engine, к которому мы переходим.»

Связка, использующая поведенческий слой — то, чего нет у `repo-analyzer`,
потому что там нет доступа к истории чужого кода как к источнику сюжета:

> ✅ «Адаптер платёжного провайдера пережил три переписывания за два года
> (см. §10 — трасса коммитов ниже): каждое пыталось изолировать провайдера
> от домена. Четвёртая попытка — модуль-шлюз, к которому переходим дальше —
> наконец вынесла эту границу в контракт, а не в реализацию.»

Правило: мост обязан называть, что именно из предыдущего модуля создаёт
необходимость в следующем (вывод, ограничение, нерешённый вопрос) — связка
без этого содержания не проходит, сколько бы в ней ни было слова «далее».

## 9. Гейт покрытия перед сборкой

1. Прочитать таблицу покрытия в конце каждого `drafts/module-*.md`.
2. Проверить итоговую строку: ✅ или ❌.
3. Только ❌-модули разбираются подробно — не трогать то, что уже ✅.
4. Не дотянувший модуль — главный агент сам дочитывает непокрытые сегменты
   и дописывает черновик, не отправляя обратно субагенту.
5. Если и после этого не дотянуто — явно сказать пользователю, какие модули
   и почему (файл нечитаемый, бинарник, чрезмерный объём) — это ограничение
   отчёта, а не находка и не повод снижать заявленный уровень задним числом.
6. Переход к сборке (фаза 7) — только когда каждый модуль либо ✅, либо имеет
   явно объяснённое исключение из п.5.

## 10. Главное отличие: поведенческий слой

`repo-analyzer` анализирует то, что лежит на диске сейчас, плюс внешний веб.
У чужого репо есть источник, которого там нет вообще — git-история: она
показывает, что уже пробовали, что переписывали, что откатывали. Recon
обязан вплетать это в нарратив, а не прикладывать отдельной главой
«история коммитов» в конце.

**Инструменты.** `zodchiy.py behavior <repo>` уже считает агрегаты
(`hotspots`, `temporal_coupling`, `containment`, `knowledge_risk`, `reverts`)
— это те же цифры, что использует `audit`, но recon берёт их описательно,
без прогона через калибровку (`measure.py`, `calibrate()`) и без превращения в R-коды с remedy.
Для точечного «что именно произошло с этим файлом» агрегатов недостаточно —
нужны прямые команды.

| Вопрос к истории | Команда | Что даёт нарративу |
|---|---|---|
| Сколько раз переписан модуль | `git log --follow --oneline -- <path>` | темп изменений, число ревизий |
| Где горячая точка (агрегат по репо) | `python3 zodchiy.py behavior <repo>` → `hotspots` | churn × размер, доля багфиксов на файл |
| Что откатывали | `git log --grep='revert\|откат' -i --oneline -- <path>`, затем `git show <sha>` на найденном | факт «было и отменили», с сообщением коммита |
| Когда и почему появилась абстракция | `git log --diff-filter=A --follow -- <path>` (дата создания), затем `git log -p -- <path>` вокруг этой даты | момент и повод появления, из текста коммита |
| Абстракция — реакция на баг или архитектурное решение | `git log -p --follow -- <path>` вокруг дат багфиксов, `git blame <path>` на конкретные строки → `git show <sha>` | мотив своими словами автора, не догадка |
| Что меняется вместе (материал для моста между главами) | `python3 zodchiy.py behavior <repo>` → `temporal_coupling`, либо точечно `git log --name-only --pretty=format:'--%H--' -- <dirA> <dirB>` | видно ли, что модуль A и модуль B всегда правятся вместе |
| Кто держит модуль на практике | `python3 zodchiy.py behavior <repo>` → `knowledge_risk`, либо `git shortlog -sn -- <path>` | один автор = наблюдение «знание сконцентрировано», не R-код (это только для audit) |

Формулировки для нарратива — конкретные, с числом и ссылкой на команду,
а не общие слова:

- «модуль переписан трижды, вот траектория: {commit1} → {commit2} → {commit3},
  каждый раз меняли ровно границу с провайдером»
- «эта абстракция появилась после N багфиксов вот здесь: {sha1}, {sha2} —
  оба чинили одну и ту же гонку, третий коммит {sha3} наконец вынес блокировку
  в отдельный слой»

Ограничение честно проговаривается, а не маскируется: если истории мало
(`behavior.py` вернёт `available: false`) — recon так и пишет, что
поведенческий слой недоступен для этого репо/модуля, и держится на двух
источниках — коде и документах.
