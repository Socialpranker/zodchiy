# Режим `prune` — мёртвый код в две фазы

Статика доказывает только лёгкую половину: на код никто не ссылается. Годами
копится другая половина, код достижимый, но не выполняемый, а удалять его по
подозрению никто не рискнёт. Поэтому режим не угадывает. Доказуемо мёртвое
удаляется сразу, на подозрительное ставится маркер, и через окно наблюдения
удаляется то, что ни разу не сработало. Схема взята у рутины чистки в Claude
Code (Boris Cherny, 13.08.2026); окно здесь меряется контрольной группой, а не
сутками, потому что у малого сервиса сутки не прогоняют половину живых веток.

## Оглавление

- Статусы
- Порядок работ
- Контрольная группа и окно
- Удаление
- Классы вне скрипта: флаги и тесты, которые не падают
- Деградация

## Статусы

| Статус | Что значит | Что дальше |
|---|---|---|
| `provable` | статика не нашла ссылок, слепых зон нет | удалить в пробе |
| `suspected` | ссылок нет, но есть слепая зона (`blind_spots`) | маркер |
| `manual` | слепая зона есть, маркер поставить некуда (класс, импорт, переменная, тело в одну строку) | решает модель, потолок `hypothesis` |
| `instrumented` | маркер стоит, вердикта ещё нет | ждать окно |
| `never_fired` | маркер ноль раз при достаточном контроле | удалить в пробе |
| `alive` | маркер сработал (`hits > 0`) | не трогать, код живой |

Слепые зоны: `decorator_registration` (роут, хендлер бота, фикстура),
`framework_hook_possible` (метод, свойство, атрибут зовёт фреймворк по имени),
`string_reference` (имя в строке: реестр, `getattr`, конфиг маршрутов),
`non_python_reference` (шаблоны, YAML, Dockerfile, Procfile),
`reflection_in_module`, `exported_in_all`, `reexport`, `standalone_script`
(модуль с кодом на верхнем уровне: его запускают руками, и в логах прода он не
появится, поэтому сразу `manual`). Список консервативный:
лишняя слепая зона стоит одного дня ожидания, пропущенная стоит удалённого
живого кода.

## Порядок работ

1. Замер для графа модулей, если его ещё нет:
   `zodchiy.py measure <repo> --out .zodchiy/measure.json`.
2. `zodchiy.py prune scan <repo> --measure .zodchiy/measure.json`. В stdout
   сводка по статусам и деградации, полное состояние в `.zodchiy/prune.json`.
   Деградации переходят в отчёт дословно.
3. Удалить `provable` (раздел «Удаление»). Это первый PR.
4. Выбрать контроль: функцию, которая точно выполняется на каждом запросе или
   апдейте (корневой хендлер, middleware). Затем
   `zodchiy.py prune instrument .zodchiy/prune.json --control app/bot.py:on_update`.
   Маркеры ложатся в рабочее дерево отдельным коммитом
   `chore(prune): маркеры исполнения`, чтобы его можно было откатить целиком.
5. **Выкатка маркеров на прод: внешне видимое действие.** Подготовь коммит и
   спроси Ивана последним шагом; без выкатки на прод окно наблюдения не идёт.
6. После окна: `zodchiy.py prune collect .zodchiy/prune.json --log <лог>`
   (несколько `--log` или `-` для stdin, например `journalctl -u svc | ...`).
   Логи подаются за всё окно одним вызовом: вердикт считается по ним заново.
   Код выхода 1 значит, что контроль ниже порога и вердикта нет.
7. Удалить `never_fired` в пробе, `zodchiy.py prune strip <repo>` снимает все
   маркеры. Это второй PR, и в нём не должно остаться ни одной строки с
   `# zodchiy-prune` (`grep -rn "zodchiy-prune"` пустой).

## Контрольная группа и окно

Ноль срабатываний маркера значит «мёртв» только рядом с маркером, который за то
же окно заведомо срабатывал. Иначе ноль одинаково объясняется коротким окном,
чужим логом или невыкаченными маркерами. Поэтому `instrument` без `--control`
не запускается, а `collect` не выносит `never_fired`, пока контроль ниже
`--min-control` (по умолчанию 20).

Порог 20 годится для ветки, которая выполняется хотя бы раз на двадцать
запросов. Редкие сценарии (месячный отчёт, ежегодная выгрузка, обработка
ошибки платежа) так не ловятся: имя такого кода в `suspected` перед удалением
сверяется с cron, планировщиком и обработчиками ошибок, а окно выбирается не
короче периода самого редкого сценария. Выбранное окно и порог пишутся в отчёт
как допущение.

## Удаление

Удаление идёт в отдельном worktree на ветке `zodchiy/prune-<YYYY-MM-DD>`, в
основное дерево ничего не пишется. После удаления в worktree прогоняются тесты
проекта, сборка или импорт точки входа и повторный `prune scan`. Тесты красные:
кандидат возвращается в `suspected` с причиной, а не чинится правкой тестов.
Удаление `provable` без зелёных тестов не принимается: тест здесь вторая ось,
которая подтверждает статику.

Удаление тянет за собой сирот: импорт, который нужен был только удалённой
функции, и тест только на неё. Их удаляет та же проба, и повторный `scan`
показывает, что новых сирот не осталось.

## Классы вне скрипта: флаги и тесты, которые не падают

Флаги фич на 0% или 100% скрипт не ищет, потому что хранилище флагов у каждого
проекта своё. Модель читает конфиг флагов, проверяет историю значения через
`git log -S <флаг>` и выносит кандидата со статусом `hypothesis`. Флаг на 100%
удаляется вместе с выключенной веткой, флаг на 0% вместе с включённой.

Тест, который не может упасть, ищется мутационным тестированием (`mutmut` для
Python): если тест зелёный при любой мутации кода под ним, он ничего не
проверяет. `mutmut` не установлен: этот класс объявляется слепой зоной, а не
пропускается молча.

## Деградация

| Чего нет | Что делаем | Где видно |
|---|---|---|
| `vulture` | ищем только модули-сироты | `degraded: vulture not found` |
| `--measure` | символы есть, модулей-сирот нет | `degraded: orphan_modules` |
| git | возраст строк не считается | `degraded: behavior`, `last_touched_days: null` |
| JS/TS | не анализируются | `degraded: js_ts` |
| доступа к логам прода | фаза 2 не идёт, `suspected` остаются в отчёте как есть | `window: null` |
